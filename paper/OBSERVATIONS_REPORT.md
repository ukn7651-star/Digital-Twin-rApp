## 0. One-paragraph summary of the whole project

An open, CPU-only, multi-cell 5G/O-RAN **digital twin** whose link-to-system (L2S) map is
grounded in OpenAirInterface's (OAI) real PHY. Pipeline: OpenStreetMap → Sionna RT ray tracing
→ per-resource-element (per-RE) SINR → EESM effective-SINR → OAI-measured `nr_dlsim` MCS curve
→ per-UE/per-cell throughput. A traffic-steering rApp closes a cell-individual-offset (CIO)
control loop on the twin. Three bridges connect it to a live OAI 5G Standalone stack. The
central research result is that a controller does **not** need the whole real PHY curve — it
needs **two scalar constants**: a fitted SINR implementation margin **δ = 4.71 dB** and a
twin→MAC derate **κ = 0.470 ± 0.004**. Two claims were **retracted** after controls (a
multi-cell fidelity gap, and a gain↔outage correlation).

---

## 1. Thesis and research questions

**Framing question:** *How much of a real physical layer does a 5G digital twin actually need
to make a RAN controller (rApp) choose the right action?*

This reframes the received wisdom. The literature says "the L2S map must be measured on real
PHY." That is true but unhelpful — it does not say *which part* of the curve a controller is
sensitive to. The contribution is to answer "which part," and the answer is "a scalar, not a
shape."

Three sub-questions, each answered by a distinct experiment:

- **RQ1 (decision sensitivity).** When two twins disagree about the SINR→throughput map, does
  acting on the wrong one *cost* anything? → the **regret** experiment (§6.2).
- **RQ2 (real-stack grounding).** How does the twin's link rate relate to what a real 5G MAC
  schedules, and to delivered goodput? → the **κ / real fidelity gap** experiment (§6.3).
- **RQ3 (multi-cell closure).** Can the loop close on real cells, and can we *measure* the
  delivered gain? → the **multi-cell** experiment (§6.4) — loop closes, measurement does not.

## 3. System architecture (→ paper Fig. 1)

**Figure asset:** rendered inline as TikZ in `main.tex` (lines 110–168). One *physics substrate*
feeds two consumers.

- **Physics substrate (shared):** WGS84 bounding box → OpenStreetMap query → footprints extruded
  into a 3D Mitsuba scene with ITU materials → Sionna RT places one TX per cell (3GPP sector
  pattern, planar array, downtilt) and one RX per UE → channel frequency response
  **H_{u,c}(k)** of *every* cell→UE link over an OFDM resource grid. Network source is swappable:
  seeded random generator (N sites × 3 sectors, uniform UE drops) or CSV of real cell coordinates.
- **Consumer 1 — analytical multi-cell twin:** per-RE SINR → EESM → Φ_OAI → per-UE rate R_u;
  KPI engine → per-UE/per-cell KPIs, outage, load → traffic-steering rApp (CIO) → closed control
  loop back into the KPI engine.
- **Consumer 2 — real-stack grounding:** three bridges (B1 channel injection, B2 interference→noise
  floor, B3 per-cell injection on 2 DUs) drive a live OAI 5G-SA core + gNB(s) + UE →
  goodput + MAC KPIs. Calibration arrow: measured MAC rate ⇒ derate κ; goodput ⇒ emulator ceiling.

**Scene visualisation (manager's request).** The ray-traced 3D scenes exist as committed assets
under [`experiments/results/scene/`](../experiments/results/scene/): `berlin_mitte/`,
`manhattan_mid/`, `paris_opera/`, each with `scene.xml` + a `meshes/` folder of per-building `.ply`
meshes (Berlin alone has thousands). These can be rendered to a hero image *if* a scene figure is
wanted — see §8 and §12 for the space trade-off. **They are not currently rendered into any paper
figure.**

## 4. Methods (equations and definitions, verbatim from the engine)

### 4.1 KPI engine
- **Association with CIO** (the O-RAN knob):
  `s(u) = argmax_c  P_rx_{u,c} · 10^(CIO_c/10)`, where `P_rx_{u,c} = P_tx_c · mean(‖H_{u,c}‖_F²)`.
- **Per-RE SINR** (airtime sharing ⇒ one UE/cell/slot ⇒ matched-filter precoder, serving per-RE
  gain σ_max):
  `γ_u(k) = p_s·σ_max(H_{u,s}(k))² / ( ρ·Σ_{c≠s} (p_c/N_t)‖H_{u,c}(k)‖_F² + N_0 )`,
  with ρ ∈ [0,1] the neighbour load and `N_0 = kTB·NF`.
- **EESM compression** (preserves frequency selectivity):
  `γ_eff_u = −β·ln( (1/K) Σ_k e^(−γ_u(k)/β) )`, β per modulation order + one scale.
- **OAI-measured curve:** `(m_u, η_u) = Φ_OAI(γ_eff_u)`, measured offline from `nr_dlsim`
  (LDPC decode, rate matching → real receiver losses).
- **Per-UE rate** (static full-buffer snapshot, PF ⇒ equal airtime):
  `R_u = (B_s/K_s)·η_u·(1 − BLER_tgt)`.

### 4.2 Traffic-steering rApp
Maximises PF utility `U(CIO) = Σ_u log R_u` by **coordinate ascent**: from CIO=0, sweep cells,
line-search each cell's CIO over grid {−12..+12} dB with others held, keep the maximiser, stop
when no line search improves U. Monotone in U by construction. Convergence: 2–3 sweeps, **4.7 s**,
9 cells. *The rApp is a reference controller, not a contribution.*

### 4.3 Regret — the key methodological device (RQ1)
Hold geometry, ray tracing, association, interference fixed; change **only** the link curve.
- **Reporting error** = distance between a surrogate twin's own predicted throughput and the
  OAI-grounded twin's.
- **Decision error = regret:** `R = U(CIO*_ΦOAI | ΦOAI) − U(CIO*_Φsur | ΦOAI) ≥ 0` — evaluate the
  surrogate's chosen CIO *on the OAI-grounded twin* and compare to what it would have chosen had it
  planned there. Units: nats of PF utility. Regret has a natural null (zero); "decisions differ"
  and Jaccard overlap do not.

**Four surrogates** over the identical (MCS, SE) set, differing only in the SINR at which each MCS
unlocks:
1. `ideal` — Shannon-optimal staircase (straw man, no simulator uses it).
2. `margin2db` — *assumed* fixed +2 dB margin (the honest link-budget abstraction).
3. `offset` — *fitted* `Φ(γ)=log₂(1+γ/δ)`, δ = 4.71 dB.
4. `attenuated` — *fitted* `a·log₂(1+γ)`, a = 0.606.

### 4.4 Bridges (real-stack)
- **B1 channel injection [VALIDATED]:** ray-traced CFR → sample-spaced impulse response (IFFT) →
  keep 4 strongest causal taps, unit-energy normalised → override rfsimulator channel via OAI patch
  `oai_rt_inject_channel`. Confirmed in gNB log. *Carries every measured fidelity number.*
- **B2 interference→noise floor [DESIGN SPEC, UNVALIDATED]:** per UE,
  `ΔN_u = 10log₁₀((I_u+N_0)/N_0)` written as per-client OAI noise power — a site-specific
  generalisation of 3GPP OCNG. *No fidelity claim.*
- **B3 per-cell injection [INJECTION VERIFIED, MEASUREMENT DOES NOT CLOSE]:** two-DU stack, UE is
  the rfsim *server*, DU-k's samples pass `rfsimu_channel_ue{k}`, `rxAddInput` sums both waveforms
  ⇒ physically combined interference, not a noise proxy.

### 4.5 Controls
- **Null control:** run the 2-cell harness with *both cells carrying the same clean channel* ⇒
  true effect is exactly 0; anything reported is instrument bias.
- **Within-scene correlation:** recompute gain↔predictor correlations *inside* each scene
  (n=8), not pooled across three cities, because a pooled correlation can be manufactured by the
  between-city contrast alone.
- **EESM β sensitivity:** perturb the twin's only unfitted knob ±20%, measure decision flips and
  regret.

## 5. Experimental setup (constants to state in the paper)

- **Scenes:** Berlin-Mitte (**2,623** buildings), Paris-Opéra (**121**), Manhattan-Midtown
  (**119**). Geometry built once per scene, reused across **8** seeded layouts each ⇒ **24 runs**.
- **Radio:** 3.5 GHz; **B = 38.16 MHz** (106 PRB @ 30 kHz SCS, matching the live OAI cell);
  46 dBm/cell; 4×1 BS array; 7 dB NF; ray depth 3; **9 cells, 30 UEs** per layout; ρ = 1.0
  nominal; CFR over all **1272 subcarriers** (full band). Load sweep varies ρ ∈ {0..1} on a cached
  channel.
- **Φ_OAI measurement:** sweep SNR × MCS through `nr_dlsim`, 106 RB, 12 frames/point, 0.2 dB
  granularity, take lowest SNR whose first-transmission BLER meets the 10% target ⇒ SINR range
  **−2.6 to 21.4 dB**.
- **Software:** OAI `develop`@`0dab3bb` (tag `2026.w27`); Sionna RT **2.0.1**; solver **seeded**
  from layout seed (an unseeded solve drifts every downstream number ~1%).
- **Runtime:** 13.1 s ray tracing + 4.7 s coordinate ascent per layout; full 24-run sweep + load
  sweep = **703 s**, CPU-only.
- **Metrics:** per-UE DL throughput (median, mean); *served cell-edge* = 5th percentile among UEs
  with non-zero throughput (a raw p5 collapses to 0 once outage > 5%); *outage* = fraction with
  zero throughput; Jain index; *peak cell load reduction* = decrease in max UEs on any one cell.
- **Clustering caveat:** 8 seeds/scene share geometry ⇒ pooled n=24 overstates effective sample;
  report 3 per-scene tests (n=8 each) alongside pooled, treat per-scene directional consistency as
  the evidence.

## 6. Results — observation by observation

### 6.1 Traffic-steering rApp helps (→ paper Table II; Fig. `fig_cdf_pooled.png`, `fig_gains_by_scene.png`)
[stats: `sweep`]

Pooled over 24 runs, vs strongest-cell association:

| Metric | Mean [95% CI] | paired p | +/−/tie |
|--------|---------------|----------|---------|
| Median tput | **+10.9%** [6.8, 14.8] | 2·10⁻⁴ (Wilcoxon) | 19/3/2 |
| Served edge | **+25.9%** [15.8, 36.9] | 4·10⁻⁴ (Wilcoxon) | 16/3/5 |
| Jain index | +6.2% [1.0, 11.6] | 0.052 (sign) | 16/6/2 |
| Peak load (UE) | −0.62 [−0.96, −0.29] | 6·10⁻³ (Wilcoxon) | — |
| Mean tput | +3.7% [1.2, 6.4] | 0.036 (Wilcoxon) | 15/7/2 |
| Outage | 0.0 (all runs) | n/a | 0/0/24 |

Absolute levels: median rate 15.8 → 18.5 Mbps; served cell-edge 5.8 → 7.4 Mbps.

**Per-scene (n=8) Wilcoxon** [stats: `paired_tests_by_scene`]:
median rate p<0.05 in Manhattan (0.0156) and Paris (0.0156) but **not** Berlin (0.148); served
edge significant in Berlin (0.0469) and Manhattan (0.0313) but **not** Paris (0.156).

**Per-scene character** [stats: `by_scene`]:
- Berlin (densest): lowest outage **10.4%**, sheds most peak load (−1.0 UE), gains least median
  rate (**+6.7%**), sign p 0.727 (5+/3−).
- Manhattan: gains most in fairness (Jain **+17.5%**), median +13.1%, sign p 0.0156 (7/0, 1 tie).
- Paris: highest outage **25.8%**, **loses** fairness (Jain **−4.5%**), median +13.0%,
  sign p 0.0156 (7/0).

**Honest caveats:** aggregate rate rises only 3.7%; Jain misses significance (p=0.052) and is
negative in Paris; **outage is bit-for-bit identical in all 24 runs** (steering relocates covered
users, does not create coverage); on 2–5 layouts the rApp moves no UE (exact-zero gain), ties
excluded from sign test per Dixon–Mood.

**Take-home for paper:** *direction robust across all three geometries; magnitude strongly
deployment-dependent — exactly what a single-scenario study misrepresents.*

### 6.2 What a twin says vs. what acting on it costs (RQ1) (→ paper Fig. 2 = `fig_l2s_regret.pdf`)
[stats: `decision_regret`, `l2s_fit`]

Fit: δ = **4.711 dB**, a = **0.6059**, fixed margin 2.0 dB.

| Surrogate | Reporting error [95% CI] | Regret nats [95% CI] (max) | Decisions differ | Threshold err RMS/max dB |
|-----------|--------------------------|----------------------------|------------------|--------------------------|
| ideal (Shannon) | +39.7% [30.4, 49.9] | 0.767 [0.036, 1.834] (8.70) | 37.5% | 4.75 / 5.81 |
| margin2db (+2 dB assumed) | +24.4% [18.2, 30.8] | 0.732 [0.011, 1.807] (8.70) | 29.2% | 2.78 / 3.81 |
| **offset (+δ fitted)** | **+1.6% [−0.1, 3.5]** | **0.033 [0.006, 0.071] (0.39)** | 25.0% | **0.62 / 1.14** |
| attenuated (a·Shannon) | −5.7% [−8.9, −2.5] | 0.800 [0.047, 1.905] (8.94) | 37.5% | 2.63 / 6.19 |

**Four readings, each a paper sentence:**
1. Fitted δ collapses both errors (23× less regret than uncalibrated).
2. Assumed +2 dB halves reporting but barely touches regret ⇒ it is δ's **value**, not a margin's
   presence, that the controller is sensitive to.
3. "Decisions differ" is 25–38% for **every** surrogate — separates none; Jaccard overlap
   (0.81–0.84) likewise has no null. Only regret has a null (zero) and separates them.
4. The attenuation model is the instructive failure: reports best (−5.7%) yet costs the most
   (0.800 nats). Its threshold error is 2.63 dB RMS but **6.19 dB max**, concentrated at the
   extremes where cell-edge/cell-centre users live ⇒ reads well, acts badly.

**Mechanism (why one scalar suffices):** OAI's staircase *is* a Shannon-optimal staircase displaced
by δ — its MCS thresholds sit 0.62 dB RMS from the fitted-offset curve across MCS 0–28. The curve's
non-uniform MCS spacing (QPSK→16QAM boundary spans 2.2 dB vs ~1 dB for adjacent QPSK steps) does not
change what the controller does.

**Link-curve fact for intro:** at 10 dB SINR the OAI curve yields 2.16 bits/s/Hz vs Shannon's 3.46
= **38% implementation loss**.

### 6.3 The real fidelity gap — the constant κ (RQ2) (→ paper Fig. 3 = `fig_real_fidelity_gap.pdf`)
[stats: `real_fidelity_gap`]

Single gNB, matched bandwidth. Pin DL operating point by capping scheduler MCS over a clean
channel, sweep the cap MCS 0–28, measure goodput at each fixed MCS. 12 calibration points, SINR
−2.6 to 21.4 dB, B = 38.16 MHz, DL duty 0.7429.

**Two references (conflating them is what makes "fidelity gap" numbers irreproducible):**

- **Twin → OAI MAC (what the scheduler schedules):** the twin's link rate `B·η_OAI·(1−BLER)` is
  high by a **constant** factor. **κ = 0.470 ± 0.004** (mean 0.4704, std 0.00374, CV **0.796%**).
  Equivalent inflation median **52.9%**, range only 52.4–53.6% over MCS 0–28.
- **Twin → delivered goodput:** high by a median **80.0%** (range 72.0–86.9%), and this is **not**
  constant (CV **27%**), growing 72%→87% from MCS 0 to 28.

**Decomposition at MCS 28:** twin predicts **190.77 Mbps**, MAC schedules **88.91**, delivered
goodput **24.90**. TDD duty (104/140 = 0.743) + MAC physical-channel/scheduler overhead (0.633)
account for the *whole* twin→MAC discrepancy — which is why κ is constant. Everything below the MAC
line (twin×TDD = 141.72 Mbps → MAC 88.91 → app 24.90) is an **upper bound** on unmodelled stack
effects (rfsim compute ceiling + same-host contention + transport), inseparable on one machine.
Mean twin link 83.14 Mbps vs mean real goodput 13.60 Mbps.

**The payoff of constancy (H7):** a multiplicative κ cancels in ratios ⇒ it should not perturb the
twin's *relative* predictions. Test: propagate each curve through the rApp over 8 layouts (240
per-UE evaluations, **19 steered UEs**), index every curve by the twin's own operating MCS (do NOT
interpolate along SINR — that compares a staircase with a ramp and manufactures a gap between the
knots). Airtime share (most of the rApp's benefit) is kept in both rates and cancels in the
difference.
- **vs MAC:** twin predicts 126.6% vs 125.4% scheduled ⇒ gap **+1.2 ± 5.7 pts**, CI **[−0.7, +4.1]
  straddles zero**. (Correlation twin-vs-MAC gain: r = 0.9991.) *The twin is right.*
- **vs delivered goodput:** median **−6 pts**, CI **[−22.2, −4.3] excludes zero**. (r = 0.9896.)
  *That residual is the emulator ceiling, not the abstraction.*

**Quote κ, not the 80%.**

### 6.4 Multi-cell closed loop — closes, but does not yet measure (RQ3) (→ Fig. `fig_null_control.pdf`)
[stats: `null_control`; README §3b–3d]

Two real cells (CU + two F1 DUs) = a two-sector twin. The rApp's decision **executes as a real
inter-cell handover** via scripted CU telnet, PDU session preserved: **the loop closes.**

*Measuring the delivered gain is a different matter, and is a documented negative result:*

- **First attempt (RETRACTED):** reported twin per-UE gain 66% overshooting delivered 9.0% by
  **57 ± 165 points**, blamed on the DUs' clean channel.
- **Null control kills it:** give both cells the *same* channel (true effect = 0), and the harness
  reports **−21.0 ± 1.4%** [stats: `null_control.arms.cochannel_tcp6.naive`]. Cause: a 6 s TCP flow
  started 3 s after each handover, inside both TCP slow start and the link-adaptation ramp; and
  `trigger_f1_ho` always moves DU0→DU1, so measurement order and cell identity were confounded —
  the reported *sign* followed whichever direction the rApp chose (mean DL MCS **16.5 on PCI 0 vs
  10.7 on PCI 1**).
- **Fixed instrument:** probing at TCP's plateau gives **−2.4 ± 2.9%** [stats:
  `null_control.arms.cochannel_plateau.balanced`], consistent with zero, MCS 28 on both cells.
- **Also invalid:** a saturating UDP probe (the textbook fix) — in reverse mode `iperf3` reports the
  *sending* rate, so an 8 Mbps offer through a 9.8 Mbps MAC reads back as 8.00 Mbps at ~0% loss
  (evidence: `iperf3_udp_reverse_evidence.txt`).

**With the instrument fixed, ground the channel (B3):**
- Injection **works and is verified** — every layout's UE log shows both per-cell models carrying
  the twin's ray-traced gains, UE reaches MCS 27 on the stronger cell (evidence:
  `multignb_injection_evidence.txt`).
- **Two remaining obstacles, neither the twin's:**
  1. With channel models on both rfsim connections the loop destabilises — over 3 layouts, 2 F1
     handovers never complete, the third only through **70 UE re-synchronisations**.
  2. rfsim's noise floor is a config knob, not `kTB·NF`. Injection sets only the *relative* per-cell
     gain; sweeping the floor −22→−2 dB gives operating MCS **8, 19, 14, 18, 14, 0** — non-monotone,
     **not invertible** [`rfsim_noise_calib.csv`]. A controlled multi-cell gap needs absolute
     operating-point matching, which this emulator cannot deliver.

### 6.5 Coverage, outage, load sensitivity (→ Fig. `fig_outage_vs_load.png`, `fig_throughput_vs_load.png`, `fig_scatter_gain.png`)
[stats: `sweep.correlations`, `sweep.outage`]

- Mean UE outage **17.8%** at full neighbour load.
- **Correlation retraction (RETRACTED):** an earlier version (sub-band CFR, band-wide EESM,
  unseeded solver) reported a confident r = −0.42 of gain vs baseline outage. With the full band +
  seeded solver it dissolves. Pooled over 24 runs, median gain correlates weakly with peak load
  (r = 0.29) and negligibly with outage (r = 0.05); recomputed **within scene** neither survives —
  peak load r = +0.46 / −0.08 / +0.18 and outage r = −0.42 / −0.29 / +0.08 (Berlin/Paris/Manhattan),
  **changing sign**. *Claim neither predictor.*
- **Regime separation (holds):** lowering ρ from 1.0 to 0 raises mean throughput **1.68–1.95×**,
  separating a coverage-limited tail steering cannot fix from an interference-limited body where
  load balancing acts.

### 6.6 EESM robustness (→ no dedicated paper figure; one paragraph in §6.2)
[stats: `eesm_sensitivity`]

| β scale | Δ mean eff. SINR | decisions differ | regret nats [CI] |
|---------|------------------|------------------|------------------|
| ×0.8 | **−0.147 dB** | 8.3% | 0.046 [0, 0.135] |
| ×1.2 | **+0.106 dB** | 4.2% | 0.005 [0, 0.016] |

Both shifts are the *same sign* as the perturbation (this was a prior bug in the paper text —
originally written "∓0.15", corrected to "under 0.15 dB"). At most 0.046 nats — same order as the
best-calibrated curve's residual (0.033), ~17× below uncalibrated (0.767). The knob does not drive
the conclusions, but is not negligible; the perturbation bounds **magnitude**, not structural error
across modulation orders. State both.

## 7. Negative results and retractions (collect these in ONE labelled subsection)

The manager's "blog" impression partly comes from these being narrated inline throughout the body.
In the paper, gather them under one heading ("Retractions and negative controls") and state each as
a finished result:

1. **Retracted: the 57 ± 165 pt multi-cell fidelity gap** — a null control on two identical cells
   read −21.0 ± 1.4% where truth is zero (§6.4). *Method contribution: run a null control before
   reporting any twin-vs-real gap.*
2. **Retracted: the gain↔outage correlation (r = −0.42)** — an artifact of pooling across three
   cities; within scene it reverses sign (§6.5). *Method contribution: report correlations within
   scene.*
3. **Negative result (documented, not retracted): controlled multi-cell gap does not close** —
   loop instability + non-invertible rfsim noise floor (§6.4). This is a genuine, reproducible
   finding about the *emulator*, worth stating as a limitation of the platform, not a failure of
   the twin.
4. **Invalidated instruments:** reverse-mode UDP iperf3 (reports send rate); post-handover 6 s TCP
   flow (measures slow-start + LA ramp). Both are methodological lessons.

## 12. Turning this into a paper — direct guidance on the manager's critique

**Why the current draft reads like a report/blog, and the fix for each:**

1. **First-person dead-end narration.** Phrases like "We tried to make it, and the evidence did not
   support it," "Our first attempt reported…," "we came to retract" thread the *process* through the
   *results*. → Move all of it into §7's single "Retractions and negative controls" subsection.
   In the body, state only the surviving claim + number.

2. **Rhetorical questions as section drivers.** "but does a controller care?", "What predicts a
   layout's gain?" read as blog. → Replace with declarative topic sentences: "A controller is
   insensitive to the curve's shape but sensitive to its offset δ (Fig. 2)."

3. **Contribution list written as narrative.** The four `\item`s in the intro embed argument and
   hedge. → Compress to noun-phrase contributions; push evidence into Results.

4. **Overloaded sentences with em-dashes and asides.** Many sentences carry three clauses. →
   One claim per sentence; move parentheticals to footnotes or the reproducibility statement.

5. **Title** is currently a question ("How Much Real PHY Does a Twin Need?"). Conference reviewers
   sometimes read question-titles as informal. → Consider a declarative alternative, e.g.
   "Two Constants Are Enough: Receiver-Grounded Link Abstraction for O-RAN Digital Twins." Keep the
   question as the framing sentence in the abstract.

6. **Overfull boxes / undefined refs.** `build.sh` already gates these to zero; the manager's copy
   was an older build. State in the cover note that the current build is 6 pages, 0 overfull, 0
   undefined, 0 errors, 61 tests pass.

- I. Introduction → §1 + the 38% link-curve fact + contributions (§2 as noun phrases).
- II. Related Work → §11 Table I + OWDT positioning.
